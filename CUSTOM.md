# What this fork adds to T3 Code

Branch `custom-v2` is the official T3 Code (`upstream/main`, pingdotgg/t3code) plus the features below.
Every sync merges upstream in with `scripts/custom/sync-upstream.sh`. Upstream's code wins every conflict, except where re-applying a feature listed here needs our side.

**Drop rule.** When upstream ships what a row does, take upstream's version, delete our code, and delete the row. Keep only the part upstream lacks.

Paths are short: `server/`, `web/`, `desktop/` and `mobile/` mean `apps/<name>/src/`; `contracts/`, `shared/`, `client-runtime/`, `provider-core/`, `provider-pi/` and `tailscale/` mean `packages/<name>/src/`.

- The inline `/` picker (fork PR #17, never merged), replaced by upstream `a01c48f862` and `deb5b3941d`.
- Archiving a project (our `projectArchiveColumn.ts`, contract fields and settings toggle), replaced on 2026-11-02 by upstream #26154 (`ffaa1dba76`, pin and archive projects, migration 076). Migration 076 is edited to add each column only when missing, because databases that ran our helper already have `archived_at` (test: `076_ProjectionProjectsPinArchive.test.ts`). We keep only hiding an archived project's threads and the Settings archive list.

**Sync check.** `sync-upstream.sh check` runs CI's lint, typecheck and unused-code commands, then three more things CI rejected on the 2026-10-19 sync: a production web build with the React Compiler reporting every component it skips (a `try`/`finally` without `catch` is one), the test files the sync added or changed (run through each package's own `test` script), and a search of the built web files for the fork's own name, which would put the "what's new" link on a fork with no releases. Any failure fails the check. The check needs the Node version in `package.json` and refuses to run on another. Before browser tests it installs the Chromium build the web and server packages' Playwright pins, as CI does. It is built for affinity-vps (Linux): on a Mac it skips test files named `*Linux*`, and the full run took about 30 minutes on 2026-10-19. It ends by printing the footprint, meaning the Upstream files the fork edits (modified or deleted at the merge-base with `upstream/main`, a rename counting as a deletion; the fork's new files never clash, so they are left out) and the lines changed in them, before and after the sync. `sync-upstream.sh footprint [ref]` prints the same for `ref` (default `HEAD`) without a sync worktree, so a pull request can quote it. `SYNC_BASE=<commit>` sets the pre-sync base when the sync's pull request has already merged. Its helpers are tested by `bash scripts/custom/sync-upstream.test.sh`.

**Conflict memory.** The script turns on git rerere. It mainly helps when an aborted sync is redone; hunks already resolved in an earlier merge do not conflict again on later merges.

**Rolling back.** A newer build may run database migrations (the 2026-10-19 sync adds upstream migrations 062–064; 063 drops old V1 projection tables), so going back to an older build is not guaranteed safe. Copy `~/.t3/userdata/statev2.sqlite` before installing.
