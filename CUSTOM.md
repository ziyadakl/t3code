# What this fork adds to T3 Code

Branch `custom-v2` is the official T3 Code (`upstream/main`, pingdotgg/t3code) plus the features below.
Every sync merges upstream in with `scripts/custom/sync-upstream.sh`. Upstream's code wins every conflict, except where re-applying a feature listed here needs our side.

**Drop rule.** When upstream ships what a row does, take upstream's version, delete our code, and delete the row. Keep only the part upstream lacks.

Paths are short: `server/`, `web/`, `desktop/` and `mobile/` mean `apps/<name>/src/`; `contracts/`, `shared/`, `client-runtime/`, `provider-core/`, `provider-pi/` and `tailscale/` mean `packages/<name>/src/`.

**Sync check.** `sync-upstream.sh check` takes about 40 seconds on affinity-vps. It runs CI's unused-code, lint and typecheck commands side by side (22 s measured on 2026-11-03), then a production web build with the React Compiler reporting every component it skips (a `try`/`finally` without `catch` is one), and a search of the built web files for the fork's own name, which would put the "what's new" link on a fork with no releases. It runs no tests: CI runs every test on the pull request. It fails when the fork edits or adds a native mobile file, because CI skips the macOS lint on `sync/upstream-*` branches on the grounds that a sync's native changes are Upstream's own. Any failure fails the check, with the failing command's last 40 lines. The check needs the Node version in `package.json` and refuses to run on another. It starts by printing the footprint (so a failing check still shows it), meaning the Upstream files the fork edits (modified or deleted at the merge-base with `upstream/main`, a rename counting as a deletion; the fork's new files never clash, so they are left out) and the lines changed in them, before and after the sync. `sync-upstream.sh footprint [ref]` prints the same for `ref` (default `HEAD`) without a sync worktree, so a pull request can quote it. `SYNC_BASE=<commit>` sets the pre-sync base when the sync's pull request has already merged. Its helpers are tested by `bash scripts/custom/sync-upstream.test.sh`.

**Merging a sync.** Pushing the sync branch starts the Mac and Linux builds (`custom-mac-build.yml`) while CI runs. When CI is green and Ziyad says merge, merge by fast-forward, `git push origin <sync branch>:custom-v2`, not with GitHub's merge button: the commit, and so the build's version, stay the same, GitHub marks the pull request merged, and `switch-build.sh` in ziyadakl/tokenmaxxing installs the build already made because its commit is on custom-v2. If the push is refused, custom-v2 moved: merge `origin/custom-v2` into the sync branch and wait for CI again.

**Conflict memory.** The script turns on git rerere. It mainly helps when an aborted sync is redone; hunks already resolved in an earlier merge do not conflict again on later merges.

**Rolling back.** A newer build may run database migrations (the 2026-10-19 sync adds upstream migrations 062–064; 063 drops old V1 projection tables), so going back to an older build is not guaranteed safe. Copy `~/.t3/userdata/statev2.sqlite` before installing.
